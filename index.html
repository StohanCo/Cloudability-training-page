Module 1 · Fundamentals

FinOps & Cloudability Fundamentals

Understand what FinOps is, why it matters, and how Cloudability (IBM Apptio) fits into the cloud financial management landscape.

What is FinOps?

FinOps (Financial Operations) is a cultural practice and discipline that brings financial accountability to the variable spend model of cloud. It enables distributed teams to make cloud spend trade-offs between speed, cost, and quality.

💡
Inform
Understand where money is being spent, by which teams, for what purpose. Visibility is the foundation of FinOps.
🔧
Optimise
Continuously improve cloud efficiency through rightsizing, commitment purchases, architecture changes, and waste elimination.
🔄
Operate
Establish repeatable processes, KPIs, and cultural practices so that FinOps becomes embedded in the way teams work.

What is Cloudability?

Cloudability, now part of IBM Apptio, is a leading cloud financial management (CFM) platform. It aggregates cost and usage data from multiple cloud providers and gives finance, engineering, and business stakeholders a unified view of cloud spend.

🌐
Multi-Cloud Support
Ingests data from AWS, Azure, and Google Cloud in a single normalised data model.
👁️
Full Visibility
Saved Views, custom dashboards, and anomaly detection give you instant answers about who is spending what.
🗺️
Business Mapping
Map cloud resources to teams, products, and cost centres using flexible allocation rules and tag governance.
💹
Optimisation
Rightsizing recommendations, RI/Savings Plan management, and commitment analytics to reduce waste.
📈
Forecasting
Statistical and ML-based forecasts help teams anticipate future spend and stay within budget.
🤝
Collaboration
Role-based access, custom reports, and scheduled exports keep every stakeholder informed.

Key Terminology

Unblended cost is the list price for each individual resource. Blended cost averages the rates of Reserved Instance or Savings Plan discounts across the organisation. Cloudability exposes both, as well as amortised cost for RI/SP accounting.

Amortised cost spreads upfront RI/Savings Plan payments over the commitment period. It gives a truer picture of daily spend than unblended, because upfront payments do not appear as large one-off charges.

Showback makes teams aware of their costs without billing them internally. Chargeback actually transfers costs to internal cost centres. Most organisations start with showback and progress to chargeback.

Unit economics express cloud cost relative to a business metric (e.g., cost per API call, cost per active user, cost per transaction). Cloudability's custom metrics feature supports unit cost calculations.

A taxonomy is the hierarchical structure used to organise cloud spend — for example, Organisation → Business Unit → Team → Product. Cloudability lets you define this hierarchy using Business Mappings and tag dimensions.

Module 2 · Getting Started

Getting Started & Data Ingestion

Connect your cloud accounts to Cloudability. This module covers prerequisites, access setup, and ingestion configuration for AWS, Azure, and GCP.

Prerequisites

🔐
Admin Access
You need administrative access to your cloud accounts and an Apptio Cloudability tenant (contact your IBM rep or admin).
🪣
Cost Export Storage
An S3 bucket (AWS), Storage Account (Azure), or BigQuery dataset (GCP) where billing exports will be delivered.
🔑
IAM Permissions
A read-only IAM role (AWS) or service principal (Azure/GCP) so Cloudability can read billing data without write access.

Cloud Provider Setup

AWS Cost and Usage Report (CUR)

AWS is connected via the Cost and Usage Report (CUR), which is the most detailed billing file available. Cloudability reads CUR data from an S3 bucket.

  1. Log in to AWS Management Console → Billing → Cost & Usage Reports.
  2. Create a new report with: Hourly time granularity, Parquet format (recommended), and include resource IDs.
  3. Deliver the report to an S3 bucket in a management (payer) account.
  4. Create a read-only IAM role (cloudability-role) with a trust relationship to the Cloudability AWS account ID.
  5. Attach a policy granting s3:GetObject, s3:ListBucket, and ce:Get*.
  6. In Cloudability → Settings → Cloud Credentials, add the IAM Role ARN and S3 bucket path.
📸
AWS CUR Configuration Screen
Screenshot: AWS Billing → Cost & Usage Reports → Create Report wizard.
View in AWS Docs ↗

Azure Cost Management Export

Azure billing data is ingested via Azure Cost Management + Billing exports to Azure Blob Storage.

  1. In the Azure Portal, navigate to Cost Management + Billing → Exports.
  2. Create a recurring export with: Daily export of month-to-date costs, storage account & container, and CSV format.
  3. Create a Service Principal (App Registration) in Azure AD with Reader role on the subscription or management group.
  4. Grant the service principal Storage Blob Data Reader on the export storage account.
  5. In Cloudability → Settings → Cloud Credentials, add the App ID, Tenant ID, Client Secret, and container details.
📸
Azure Cost Export Configuration
Screenshot: Azure Portal → Cost Management → Exports panel.
View in Azure Docs ↗

GCP Billing Export to BigQuery

Google Cloud billing is exported to BigQuery. Cloudability reads from BigQuery to ingest GCP cost data.

  1. In the GCP Console → Billing → Billing Export, enable Detailed usage cost export to BigQuery.
  2. Specify the project and dataset where billing data will be stored.
  3. Create a Service Account with BigQuery Data Viewer and BigQuery Job User roles on the billing export dataset.
  4. Download the service account JSON key.
  5. In Cloudability → Settings → Cloud Credentials, add the GCP project ID, dataset, and service account credentials.

Module 3 · Cost Visibility

Cost Visibility & Reporting

Cloudability's reporting engine lets you slice and dice cloud spend in any dimension. Learn about Saved Views, dashboards, anomaly detection, and how to build actionable reports.

Saved Views

A Saved View is a reusable filtered and grouped cost report. You can filter by cloud provider, service, account, tag, region, and dozens of other dimensions, then save the configuration for repeated use or sharing with stakeholders.

🔍
Filters
Narrow down to a specific cloud, account, region, service, or any tag-based dimension. Combine multiple filters with AND/OR logic.
📐
Group By
Pivot the data by any dimension — team, product, environment, service type — to understand cost distribution.
📅
Date Ranges
Compare this month to last month, use rolling windows, or define custom date ranges to spot trends.
📤
Export & Schedule
Export to CSV or schedule automated email delivery of reports to stakeholders on a daily, weekly, or monthly cadence.
📸
Cloudability Saved Views Interface
The Saved Views screen shows cost trend charts, grouped spend table, and filter controls.
View Cloudability Help Docs ↗

Anomaly Detection

Cloudability's Anomaly Detection engine uses statistical baselines to automatically surface unusual cost spikes. When a service or account exceeds its expected spend band, an alert is raised in the dashboard and (optionally) via email.

🚨
Automatic Alerts
Set sensitivity thresholds so you're notified only for genuinely unexpected deviations, not routine growth.
🔎
Root Cause Drill-Down
Click an anomaly to see exactly which service, resource, or account drove the spike.
🔔
Custom Notification Channels
Route alerts to email, Slack, or webhook endpoints so the right team is notified immediately.

Dashboards

Cloudability ships with pre-built dashboards for executive summaries, per-team cost reports, and commitment coverage. You can also build custom dashboards by composing widgets from Saved Views, charts, KPI tiles, and tables.

Module 4 · Allocation & Tagging

Allocation & Tagging

Accurately attributing cloud costs to teams and products requires a consistent tagging strategy and a well-defined allocation taxonomy. This module covers tag governance, business mapping, and allocation rules.

Why Tagging Matters

Without tags, all cloud costs appear as a monolithic bill. Tags allow you to attach metadata to resources (e.g., team=platform, env=production) so that Cloudability can filter, group, and allocate spend accurately.

🎯
Cost Attribution
Tags enable 1:1 mapping of resources to teams, products, or cost centres — the foundation of showback and chargeback.
📏
Consistency
A standardised tagging taxonomy ensures everyone uses the same keys and values, reducing data quality issues.
🔒
Governance
Tag policies and enforcement (via AWS Tag Policies, Azure Policy, or GCP Organisation Policies) prevent untagged resources.

Business Mapping in Cloudability

Business Mapping is Cloudability's allocation engine. It creates a virtual hierarchy (Organisation → Business Unit → Team → Product) that overlays onto the raw billing data, so costs can be reported in business terms even when tagging is incomplete.

Create custom dimensions that map to your organisation's structure. For example, a dimension called Business Unit might map tag values team=platform and team=sre to the "Infrastructure" business unit.

Rules are evaluated in priority order. Each rule specifies a filter (e.g., account=prod-123) and a target dimension value (e.g., BU=Engineering). Unmatched spend can be assigned to a "Shared" bucket or distributed proportionally.

Shared infrastructure (networking, security tools, logging) can be distributed to consumers using fixed percentages, proportional spend, or custom weightings. Cloudability supports all three allocation methods.

Compare allocated totals to raw totals and audit the "unallocated" percentage. A healthy allocation rate is above 90%. Work with teams to improve tag coverage and refine rules.

Module 5 · Optimisation

Optimisation & Waste Reduction

Cloudability surfaces actionable recommendations to reduce cloud spend through rightsizing, commitment-based discounts, and waste elimination.

Rightsizing Recommendations

Rightsizing identifies over-provisioned compute instances where CPU, memory, and network usage is consistently below a threshold. Cloudability's rightsizing engine analyses 14–30 days of CloudWatch/Azure Monitor/GCP metrics and recommends a smaller instance type.

📉
Downsize Candidates
Instances with <20% average CPU and <40% peak CPU are often safe to downsize by one size class, saving 30–50% on that resource.
🗑️
Idle Resource Identification
Resources with zero utilisation (stopped instances, unused volumes, orphaned snapshots) are flagged for termination.
🔄
Generation Upgrades
Older instance generations often cost more for the same performance. Cloudability flags instances that can move to a newer generation at a lower price.
📸
Cloudability Rightsizing Dashboard
The rightsizing screen lists each recommendation with estimated monthly savings, confidence score, and a one-click action link to the cloud console.
View Cloudability Help Docs ↗

Reserved Instance (RI) Management

Reserved Instances (AWS) provide up to 72% discount over On-Demand in exchange for a 1- or 3-year commitment. Cloudability tracks RI coverage, utilisation, and provides purchase recommendations.

📊
RI Coverage
Shows what percentage of eligible instance hours are covered by RIs. Target >80% coverage for stable workloads.
✅
RI Utilisation
Shows whether purchased RIs are being fully used. Underutilised RIs waste money; consider selling them on the AWS Marketplace.
🛒
Purchase Recommendations
AI-powered suggestions for which RI types, terms, and quantities to buy based on your usage history and forecast.

AWS Savings Plans

Savings Plans are flexible commitment-based discounts that apply to any EC2 instance type, Lambda, and Fargate usage. They are simpler to manage than RIs because they are not tied to a specific instance type.

Waste Reduction Strategies

Beyond rightsizing and commitments, significant savings come from eliminating waste entirely. Common waste categories include:

💾
Orphaned Storage
Unattached EBS volumes, old snapshots, and unused S3 data. Often accumulate silently and can represent 10–20% of storage costs.
🌐
Unused Load Balancers & IPs
Provisioned but inactive Elastic Load Balancers and Elastic IP addresses incur charges even when idle.
🌙
Non-Prod Scheduling
Dev/test environments running 24/7 instead of only during business hours. Scheduling saves 60–70% on non-prod compute.
📡
Data Transfer Optimisation
Cross-region and cross-AZ data transfer can be expensive. Architecture reviews to co-locate services in the same AZ reduce transfer costs.
Module 6 · Budgeting & Forecasting

Budgeting & Forecasting

Cloudability's budgeting engine lets teams set spending limits and receive alerts when they approach or exceed them. The forecasting module uses statistical models to project future spend.

Creating Budgets

A budget in Cloudability is a monetary target applied to any filtered dimension — a specific cloud account, a business unit, a team tag, or a combination. Budgets can be:

📅
Monthly / Annual
Set a fixed monthly or annual limit that resets at the start of each period.
📈
Growth-Based
Automatically adjust the budget each month by a fixed percentage (e.g., +5%) to reflect planned growth.
🔔
Alert Thresholds
Set multi-stage alerts at 70%, 90%, and 100% of the budget to give teams early warning.
👥
Team Assignment
Assign budget ownership to a team or individual so they receive alerts and are accountable for spend.

Forecasting

Cloudability's forecasting module projects month-end spend and annual run-rate based on your recent cost history. Two primary methods are used:

Fits a linear regression model to recent daily spend. Best suited for teams with steady, predictable growth patterns. Cloudability shows the confidence interval so you know how reliable the projection is.

For teams with cyclical patterns (e.g., end-of-month batch jobs, seasonal traffic spikes), Cloudability decomposes spend into trend + seasonal + residual components, producing more accurate projections.

Model the impact of planned changes — e.g., "what if we migrate this workload to a different instance type?" or "what if we purchase $50k of RIs?" — against the baseline forecast to see projected savings.

Module 7 · Advanced Topics

Advanced Topics

Deep-dive into business mapping architecture, forecasting nuances, the Cloudability API, and container/Kubernetes cost allocation.

Business Mapping Deep-Dive

Business Mapping in Cloudability supports multi-level hierarchies, overlapping rules, and proportional distribution. Understanding the rule evaluation order is critical for accurate allocation.

Rules are evaluated top-to-bottom. The first matching rule wins. Place the most specific rules at the top and the catch-all rules at the bottom. A "default" rule at the very end captures any unmatched spend.

Cloudability supports up to 10 levels of nesting. A typical structure: Org → Division → BU → Team → Project. Each level is a separate dimension, and parent-child relationships are defined by mapping lower-level values to higher-level categories.

Shared services costs can be distributed proportionally based on each team's direct spend or a custom metric. Cloudability recalculates this distribution each billing period, so it stays accurate as team sizes change.

Tags come directly from cloud resources. Custom dimensions are virtual groupings that exist only in Cloudability. Use custom dimensions when tags are missing, inconsistent, or when you need a business hierarchy that doesn't map 1:1 to tag values.

Forecasting Nuances

Accurate forecasting requires understanding the limitations and behaviours of the statistical models.

⚠️
Data History Length
Models need at least 60 days of stable data for reliable projections. New accounts or major architectural changes will skew forecasts.
🔢
Amortisation Impact
Upfront RI/SP payments appear as spikes in unblended cost. Always forecast using amortised cost for accurate projections.
📊
Anomalies & Outliers
One-off spikes (incident recovery, data migration) can skew linear models. Cloudability allows manual outlier exclusion.
🗓️
Seasonal Patterns
Retail/e-commerce workloads with holiday spikes need seasonality-aware models or manual budget overrides for peak periods.

Cloudability API & Integrations

The Cloudability REST API exposes most of the platform's data and configuration endpoints, enabling automation and integration with internal tooling.

📡
Cost Data API
Query cost data programmatically using the same filters and dimensions available in the UI. Useful for custom dashboards and internal charge-back systems.
🤖
Webhook Alerts
Forward budget and anomaly alerts to Slack, Microsoft Teams, PagerDuty, or any HTTP endpoint via webhook integrations.
🔄
RBAC & SSO
Manage user access via the API or integrate with your IdP using SAML/OIDC SSO for centralised user provisioning.
📥
Data Export
Programmatically export cost data to data warehouses (Snowflake, BigQuery, Redshift) for advanced analytics and BI tooling.

https://app.cloudability.com/api/1/

Container & Kubernetes Cost Allocation

Kubernetes clusters pool compute resources across many workloads, making per-team cost attribution complex. Cloudability's Container Cost Allocation feature solves this by integrating with cluster metrics.

⚙️
Agent-Based Collection
The Cloudability metrics agent (deployed as a DaemonSet) collects CPU, memory, and GPU request/limit data per Pod and Namespace.
📦
Namespace Attribution
Costs are split across Namespaces based on resource requests. Namespaces map to teams via Kubernetes labels, which flow through to Cloudability Business Mapping.
💡
Idle Cost Handling
Cluster-level idle capacity (over-provisioned nodes) can be attributed proportionally, allocated to a shared bucket, or excluded from team reports depending on your policy.
🔗
EKS, AKS, GKE Support
Cloudability natively supports Amazon EKS, Azure AKS, and Google GKE clusters with pre-built integration guides for each.
📸
Kubernetes Container Cost View
Shows per-namespace cost breakdown with CPU/memory efficiency scores and idle cost allocation.

Module 8 · FinOps Best Practices

FinOps Best Practices & Operating Model

FinOps is as much about culture and process as it is about tooling. This module covers the FinOps operating model, team structure, the Crawl/Walk/Run maturity model, and key KPIs.

The FinOps Operating Model

The FinOps Foundation defines a cross-functional team model where Engineering, Finance, and Product collaborate on cloud spend decisions. A central FinOps team (or Centre of Excellence) provides tooling, standards, and enablement.

👷
Engineering
Implements optimisations, maintains tagging standards, and responds to rightsizing recommendations. Owns cost at the resource level.
💼
Finance
Provides budget forecasts, validates allocations, reconciles cloud bills with GL, and communicates variance to leadership.
🎨
Product / Business
Owns the cost-to-value trade-off. Decides which optimisations to pursue based on business impact vs. engineering effort.
⭐
FinOps CoE
Central team that manages the platform (Cloudability), defines standards, runs the monthly FinOps working group, and drives cultural change.

Key Performance Indicators (KPIs)

📊
Allocation Rate
% of cloud spend attributed to a cost centre or team. Target: >90%.
⚡
RI/SP Coverage
% of eligible compute hours covered by commitments. Target: >80% for stable workloads.
💸
Waste %
% of total spend identified as waste (idle, over-provisioned). Target: <5%.
🎯
Budget Variance
Actual vs. forecasted spend. Target: ±10% accuracy. Large negative variance = over-spending; positive = under-utilisation.
📉
Unit Cost Trend
Cloud cost per unit of business value (per user, per transaction). Should decrease over time as efficiency improves.
🏷️
Tag Compliance
% of resources with all required tags applied. Target: >95% compliance across all mandatory tags.
